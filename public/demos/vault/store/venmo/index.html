Sandbox Testing Notes

Venmo's sandbox doesn't offer clickable test values the way Card/ACH do — there's no "bad QR code" to scan for a decline. These are informational, not click-to-fill.

The app-switch/QR screen shows a generic test merchant with Braintree's own logo instead of "Braintree Demo Suite" — that's expected sandbox behavior, not a config bug on this page.
A successful scan + approve in the Venmo app always resolves to a fixed test user named VenmoJoe, regardless of which real Venmo account does the scanning.
Venmo doesn't support true end-to-end negative-path testing via the interactive app-switch flow the way this page's button works — there's no equivalent to typing a decline-triggering card or account number.
Negative testing for Venmo happens server-side instead, by passing a fake nonce (e.g. fake-token-issuance-error-venmo-account-nonce) directly to a server-side transaction.sale() call — bypassing tokenize() entirely. That doesn't fit this page's real click-through flow, so it isn't wired up here.
single_use (used on the One Time Payment → Venmo demo) cannot be vaulted at all. This page uses multi_use specifically so the resulting payment method can actually be charged later from Vault → Charge Vaulted.
